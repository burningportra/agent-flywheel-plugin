# Phase 4: APR-Pro Blunder Hunt

**Date**: 2026-05-05
**Researcher**: claude-opus-4-7 (Phase 4)
**Project**: Automated Plan Reviser Pro (apr) v1.2.2
**Sources**: GitHub commits, issues #1–#4, BATS regression tests, `apr` script (~6,900 lines)

Operational landmines, undocumented gotchas, regrets the README does not advertise. Each item: the footgun, evidence, why it bit them, and the flywheel analog.

---

## B1. Monkey-patching a third-party `node_modules` file (Oracle's `assistantResponse.js`)

**Footgun.** APR uses `sed -i` to mutate four numeric literals inside `@steipete/oracle/dist/src/browser/actions/assistantResponse.js` to extend stability thresholds (so GPT Pro Extended Thinking does not get truncated). It writes a `.apr-backup` next to the file and adds a marker comment.

**Evidence.**
- Commit `8d8f2c0`/`fe7ce41` family: `feat(apr): add Oracle stability threshold patching for GPT Pro Extended Thinking`. The script defines `patch_oracle_stability_thresholds()`, `find_oracle_assistant_response()`, `restore_oracle_from_backup()`.
- `apr` lines ~700–820 (`patch_oracle_stability_thresholds`).
- Followup commit explicitly notes: "Document behavior when Oracle is updated (backup may become stale)".

**Why it bit them.** Sed-substitution is keyed on the *exact* literal `const requiredStableCycles = shortAnswer ? 12 : 6;`. When Oracle ships a new release that changes the literal (e.g. shortAnswer ? 10 : 6;), the sed becomes a silent no-op — patch returns success because the marker is appended, but the thresholds are not actually changed. The marker check (`grep -q APR_PATCHED_STABILITY_THRESHOLDS`) also bypasses the patch on subsequent runs even if Oracle has been re-installed and the file is now unpatched-but-marked from a prior install. Stale backups become time-bombs: a `restore_oracle_from_backup` after Oracle has been upgraded restores an *older* `assistantResponse.js`, downgrading the user's Oracle install without telling them.

**Flywheel analog.** In flywheel, this would manifest as plugin-versioned MCP tools where a flywheel skill mutates a sibling tool's runtime files (e.g. ntm pane templates, Agent Mail config). Mitigation: never mutate another package's installed files. If you must change behavior, fork-and-vendor the file under your own namespace, or expose the knob upstream and hard-pin the dependency.

## B2. Auto-checksum CI race against PR checksum-consistency check

**Footgun.** APR enforces SHA-256 checksum files committed alongside `apr` and `install.sh`. CI verifies they match. A second workflow auto-updates checksums on push to `main`. The two race.

**Evidence.**
- Commit `fix(ci): skip checksum job on main pushes to avoid race condition`: "The checksums job was failing because it ran concurrently with the auto-checksum.yml workflow… This creates a race condition where CI always fails on main pushes."
- Subsequent commit `fb23f92` `fix: update apr.sha256 to match current script` — manual fix when the auto-sync also misfired.
- `pre-commit-checksum` hook + `Makefile install-hooks` added as belt-and-braces.

**Why it bit them.** The "publish artifact + verify artifact in CI" pattern is fundamentally racy when verification runs on the same ref as publication. The eventual fix was to skip the consistency check on `main` entirely — which means `main` is no longer enforced, only PRs are.

**Flywheel analog.** In flywheel, this would manifest as the dist-drift checker (`flywheel_doctor` `dist drift`) racing `release.yml` autobuilders, or as `bd sync`/`br sync` JSONL artifacts being regenerated by both a hook and CI. Mitigation: derive checksums at install time from the commit, not from a sibling file in the same commit; or move the verification to a job that runs *after* auto-update on `main`, gated on the autosync workflow's success.

## B3. `release_lock` deleted lock files it did not create

**Footgun.** When `flock(1)` is unavailable, APR falls back to file-based locking. The original `release_lock` blindly `rm -f`'d the lock file in the trap, which could delete a lock owned by a *different* process that just took it.

**Evidence.**
- `tests/unit/test_lock_bug.bats` exists explicitly to regression-test this. Test docstring: "Verifies that release_lock does not delete lock files it didn't create (when falling back from flock). This catches the lock file preservation bug that could cause concurrent processes to interfere with each other."
- Commit `Fix locking and background concurrency` (refs `automated_plan_reviser_pro-hk5`).
- Current `apr` still has `if [[ -n "$APR_LOCK_FILE" && -f "$APR_LOCK_FILE" ]]; then rm -f "$APR_LOCK_FILE"` — defended by `background_lock_detach_parent` clearing `APR_LOCK_FILE` in the parent before the trap fires.

**Why it bit them.** Bash trap handlers run on EXIT/INT/TERM regardless of whether the process actually owned the lock. The fix isn't to delete differently — it's to clear `APR_LOCK_FILE` in the parent shell as soon as the lock is handed off to the background child, so the trap is a no-op.

**Flywheel analog.** Flywheel uses Agent Mail file reservations, ntm robot-mode session files, and br/bv worktree state. Mitigation: any cleanup hook that touches shared state must verify ownership (PID, instance UUID) before unlinking. If you cannot prove ownership, leak the file — let the next start-up reap it via stale-detection.

## B4. `diff_rounds` showed diffs backwards

**Footgun.** The dashboard "diff round 4 vs 5" displayed the diff with arguments swapped (new-then-old instead of old-then-new), making additions look like deletions and vice versa.

**Evidence.**
- `tests/unit/test_diff_bug.bats`: regression test with explicit fixtures `round_3.md` (content_A), `round_4.md` (content_prev), `round_5.md` (content_B), checking diff_rounds compares chronologically.
- Commit `test(unit): add regression tests for diff ordering and lock file bugs`: "This catches the dashboard diff argument order bug where diffs were showing backwards."

**Why it bit them.** The single-arg form (`diff N` meaning "N vs N-1") and the two-arg form (`diff old new`) had ambiguous orientation. A user reading the dashboard would have made wrong decisions about whether the spec was growing or shrinking — directly poisoning the convergence-by-eye signal.

**Flywheel analog.** In flywheel, this would manifest as `flywheel_review` showing plan-vs-impl diffs in the wrong direction, or as `flywheel_drift_check` reporting "removed" when it meant "added." Mitigation: name the parameters explicitly (`baseline_round`, `candidate_round`), never positional, and golden-file-test the diff-rendering layer with a known asymmetric fixture.

## B5. Inline-paste workaround masking the *real* bug: file uploads to ChatGPT silently corrupt

**Footgun.** APR originally uploaded README/spec/impl as ChatGPT file attachments. Uploads were "unreliable." The fix was to switch to inline pasting (`--browser-attachments never`) — i.e., shove the entire bundle into the prompt.

**Evidence.** Commit `dee5912` `fix(apr): use inline pasting instead of file uploads for GPT Pro`: "File uploads to ChatGPT are unreliable; inline pasting works consistently. Also removed orphaned duplicate code (78 lines) causing syntax error."

**Why it bit them.** "Unreliable" is doing a lot of work in that commit message — it never specifies *how* uploads failed (silently dropped? truncated? attached but not read?). The mitigation is a pure workaround: every prompt now bloats with full document text, which inflates token counts and increases the truncation risk that B1's monkey-patch is trying to solve. Two latent bugs are being papered over by stacking workarounds. And the commit also fessed up to *78 lines of orphaned duplicate code* sitting in the script.

**Flywheel analog.** Flywheel's `flywheel_plan` / `flywheel_review` payloads for Codex/Gemini fallback — if any provider's "attachment" channel is flaky, we will be tempted to inline everything and burn tokens. Mitigation: when you decide a provider channel is "unreliable," instrument it (log the failure mode) before working around it; otherwise the workaround becomes load-bearing and you cannot tell when the underlying bug gets fixed upstream.

## B6. Convergence detector cannot detect oscillation

**Footgun.** The convergence score is `0.35*output_trend + 0.35*change_velocity + 0.30*similarity_trend` with a hard threshold of `>= 0.75`. All three signals are *first-half-vs-second-half averages* over recent rounds. None of them measure *direction reversal*.

**Evidence.** `apr` lines ~2480–2820, `calculate_convergence`, plus the docstrings:
- `output_trend`: "Compares average output size of first half vs second half of recent rounds."
- `change_velocity`: "Lower average diff_ratio indicates convergence."
- `similarity_trend`: "Higher average similarity indicates convergence."

**Why it bit them.** A spec that grows in round 4, shrinks in round 5, grows in round 6 (oscillation) will show *low average diff_ratio* — APR will *correctly* compute that the average change is small, then *incorrectly* declare convergence. The detector only knows monotonic decline. Worse: the `estimated_rounds_remaining = (1 - score) * 5` formula is a linear estimate against a non-linear, possibly non-monotonic process — it will gaslight users about how close they are. There is also no minimum signal floor: if `bc` is missing, the function silently emits all-zeros and returns success.

**Flywheel analog.** Flywheel's "is the plan ready for beads?" check or "is review converged?" gate. Mitigation: detect oscillation explicitly (sign-flip count of round-to-round delta > N => "diverging"), and gate convergence on *direction agreement across signals*, not just average. Refuse to estimate `rounds_remaining` for non-monotonic series.

## B7. Session-recovery via Oracle reattach is best-effort and silently gives up

**Footgun.** When `validate_output_file` flags the round output as truncated, APR attempts a "recovery" by calling `oracle session <slug> --write-output <recovery_file>`. If recovery itself fails or also yields a truncated file, the *original* (truncated) `round_N.md` stays on disk and gets committed.

**Evidence.** `apr` lines ~3308–3332:
```
if "${ORACLE_CMD[@]}" session "$slug" --write-output "$recovery_output_file" 2>/dev/null; then
    if validate_output_file "$recovery_output_file"; then
        mv "$recovery_output_file" "$output_file"
        ...
        recovery_success=true
    else
        rm -f "$recovery_output_file"
    fi
else
    rm -f "$recovery_output_file" 2>/dev/null
fi

if [[ "$recovery_success" != "true" ]]; then
    ...  # proceeds anyway, original truncated round_N.md remains
```

**Why it bit them.** A workflow that runs unattended (e.g. via `apr run 5` in background) will silently produce a truncated round, fail recovery, and downstream metrics will compute convergence on a *garbage round*. The oscillation case in B6 then hides the corruption further.

**Flywheel analog.** Long-running tmux pane work where the agent is killed mid-bead. Mitigation: any "recovery failed, proceed" path must (a) move the bad output aside with a `.truncated` suffix instead of leaving it in place, (b) refuse to update metrics with the partial round, and (c) emit a structured error code that automation can detect and refuse to gate on.

## B8. `--notify` flag passed unconditionally to Oracle without version check

**Footgun.** APR shipped passing `--notify` to all Oracle invocations. Oracle <0.7.6 does not recognize the flag. APR's auto-retry logic re-attempted the same broken command three times, then exited.

**Evidence.**
- Issue #1 "[BUG] No --Notify Command" — user runs `apr run 1 --login --wait`, gets `error: unknown option '--notify'` repeated 3× across retries before all attempts fail.
- Fix in commit `e47d067` (`fix: make --notify flag conditional on Oracle version support`): now greps `oracle --help` to detect support, only adds `--notify` when present.
- Followup `Fix Oracle --notify detection across modes` (`7ac0272`) — the first fix didn't cover all invocation sites.

**Why it bit them.** Two compounding mistakes: (1) no upstream version pinning despite hard runtime coupling, (2) the auto-retry loop retries on *any* nonzero exit — including deterministic argument errors that will never succeed. Three retries on a `--notify` typo wastes 40+ seconds and a chrome session every time.

**Flywheel analog.** Flywheel calling `ntm`, `br`, `bv`, Agent Mail with version-coupled flags. Mitigation: classify exit codes before retrying (argument errors → no retry, transient errors → retry). Always feature-detect external tools at preflight, not at first call.

## B9. Robot-mode `APR_ERROR_CODE=...` tag emitted on stderr — interferes with BATS `run`

**Footgun.** In robot mode, fatal errors emit `APR_ERROR_CODE=<code>\n` to stderr so automation can grep for it. But BATS' default `run` captures stdout+stderr together; the tag pollutes stdout-style assertions.

**Evidence.**
- Commit `28a6e7a` `fix(tests): Use capture_streams for robot error handling test`: "The robot_fail function emits APR_ERROR_CODE to stderr, which was interfering with bats' run command. Switching to capture_streams properly separates stdout/stderr."
- Required adding a custom `capture_streams` helper across all robot tests.

**Why it bit them.** Their *own* test framework couldn't parse their *own* error envelope. A user piping `apr robot ...` through `jq` will hit the same problem if they don't use `2>/dev/null`.

**Flywheel analog.** Any flywheel MCP tool that emits structured-error tags on stderr while expecting stdout to stay clean JSON. Mitigation: pick a single channel for machine-readable output (stdout only), reserve stderr for human prose, and document this contract in the tool's MCP description.

## B10. Headless / `--engine api` blocked for ~3 months — browser engine hardcoded in three places

**Footgun.** Despite Oracle supporting `--engine api`, APR hardcoded `--engine browser` at three call sites (lines ~3238, ~5768, dry-run echo at ~3202). On any headless server (the dominant flywheel deployment), this turned APR into a non-starter unless the user ran `oracle serve` on a separate display-equipped machine over Tailscale.

**Evidence.** Issue #4 (open 2026-03-12, closed 2026-03-15 with promise to "implement independently"; no implementation commit visible in main yet at the time of this research). Body: "APR currently hardcodes `--engine browser` in all three Oracle invocation points… This made sense when GPT Pro Extended Thinking was only available via the ChatGPT web UI. But that's no longer the case."

**Why it bit them.** APR was architected around *one* engine. Adding a second engine requires touching every Oracle invocation site, every flag-builder, the dry-run echo, and the `--browser-*` flag handling. The dry-run-echo's hardcoded `--engine browser` is especially insidious: even if a user adds `engine: api` to their YAML, the dry-run preview will still show `--engine browser`, leading to "looks fine, fails on real run."

**Flywheel analog.** Hardcoded provider assumptions in `flywheel_plan` / `flywheel_review` (Codex vs Opus vs Gemini). Mitigation: route all provider calls through a single `provider_invoke()` shim; never fan flag-construction logic across N invocation sites.

## B11. `set -euo pipefail` + `bc` optional dependency = silent zero-confidence convergence

**Footgun.** `calculate_convergence` checks `command -v bc`, and if absent emits `confidence: 0.0` with `print_warning "bc not available; convergence disabled"`. But `print_warning` goes to stderr; in robot mode the JSON consumer never sees it, and the convergence object is structurally valid — `detected: false, confidence: 0.0`. A robot loop checking "while not converged, run another round" will run forever.

**Evidence.** `apr` lines ~2716–2728 (`calculate_convergence` `bc` fallback) plus the convergence-loop pattern documented in the README ("rounds 8+: <1% delta — converged").

**Why it bit them.** The script papers over a missing dependency by emitting "no signal" instead of refusing to run. The error class should be `dependency_missing` (already in their taxonomy), not "looks like signal but isn't."

**Flywheel analog.** Any flywheel pipeline step that gracefully degrades a *gating* signal to a permissive default (e.g., "if jq missing, skip metrics, continue"). Mitigation: gating logic must be on the strict path — missing dependencies in convergence/safety checks must be `exit dependency_missing`, not "0.0 confidence."

## Summary

The pattern across these blunders: APR pays the predictable price of integrating tightly with a third-party browser-automation tool whose internals it doesn't control. The monkey-patch (B1), the inline-paste workaround (B5), the unconditional `--notify` (B8), the hardcoded engine (B10), and the recovery-on-truncation (B7) are all symptoms of "we have to coerce Oracle into doing X reliably." A second cluster (B2, B3, B9) is bash-scripting hygiene around concurrency and stream discipline. The third (B4, B6, B11) is metric-engineering naïveté: averages without direction, thresholds without floors, missing-deps that look like real signal.

For flywheel: the most-translatable lessons are (a) never mutate a sibling tool's installed files, (b) classify exit codes before retrying, (c) detect oscillation explicitly in any "ready to ship" gate, (d) machine-readable error channels must be one-stream-only, (e) gating signals fail-closed on missing dependencies.
